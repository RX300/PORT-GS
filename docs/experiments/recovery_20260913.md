# Full benchmark interruption and recovery — 2026-09-13

This note records the interruption review for
`runs/full_benchmark_20260913/`. It covers process control and recovery only;
the fixed training and evaluation protocol is unchanged.

normal scheduler snapshot was written at `2026-09-12T17:23:51Z` (02:23:51

The last queue event was `startup_confirmed` for PORT Fish. The GS3 Cat log

## Script defects established by inspection

The original [run_benchmark.py](../../run_benchmark.py) writes status at phase
milestones and only writes the final queue state after both worker threads
join. It has no `SIGTERM`, `SIGHUP`, or `SIGINT` handler and no outer cleanup
path for an external termination. A kill between those writes leaves the last
snapshot as `state: running`, even when every process has exited. `SIGKILL`
would remain uncatchable even after adding a signal handler.

The original [launch_full_benchmark.sh](../../launch_full_benchmark.sh) only
set the environment and `exec`-ed the Python scheduler. Its lifetime was
therefore inherited from the caller. The current launcher starts separate
queue and monitor windows in the named tmux server
`port-full-benchmark`, keeps exited panes for inspection, and delays the
first monitor sample by 60 seconds. This removes ordinary shell disconnect as
the only lifetime owner. A tmux server started inside a supervisor that kills
its entire cgroup still needs host-side verification.

The monitor samples once, waits 3,600 seconds, and writes a record only after
the Luna call returns. The first run consequently has no record covering an
interruption before the next sample. The current monitor checks the recorded
`scheduler_pid` and reports a running queue whose scheduler PID is absent as
`interrupted`; it remains read-only and does not rewrite the scheduler status.

The new `--resume` path in `run_benchmark.py` preserves completed phase states
from `status.json` and resets only incomplete phases to `pending`. It is a
queue recovery operation, not checkpoint continuation: an incomplete training
phase is launched again from its manifest command, and `history.jsonl` is not
interpreted as a training checkpoint. Completed CatSmall and CupFabric phases
can therefore be skipped while interrupted GS3 Cat and PORT Fish phases are
queued again.

The new status and monitor paths require `scheduler_pid` in `status.json`.
Fresh runs write it before workers start. Legacy status files without that
field must be migrated or replaced before using `--status` or the monitor.

The first recovery attempt also exposed a separate queue interaction. The
resumed scheduler started at `2026-09-13T04:02:59Z` (13:02:59 JST), launched
PORT Fish on GPU 0, and then the SSD Cat evaluator failed at
`2026-09-13T04:03:08Z`. Its preserved log reports the existing SSD evaluator
`RuntimeError` from a non-contiguous tensor passed to `view`; this is a
baseline evaluator failure, not a PORT training failure. The scheduler marked
the queue `failed` while the other worker was still training Fish. A worker
failure sets the shared stop event, but the already-running phase is not
terminated immediately. The monitor must therefore inspect worker/child PID
state before treating a `failed` snapshot as quiescent.

This SSD failure cannot explain the original 02:26 interruption: no SSD phase
had started in that first run. The failed evaluator output and the interrupted
PORT output were preserved under
`SSD-GS/runs/real_fixed_calibration_20260913/Cat_failed_tensor_view/` and
`PORT-GS/runs/full_benchmark_20260913/failed_ssd_metric_20260913/`. The
independent SSD evaluation entry was then repaired to compute PSNR with a GPU
`square().mean()` path and to record `unitRGBMSE`; the upstream SSD source was
left unchanged. The queue was respawned and continued with the remaining SSD,
PORT, SSS-GS, and GS3 jobs.

Persistence is now confirmed at the host level: tmux server PID 77972 has
PPID 1 and remained alive after the launching tool command exited. This is
the evidence that the canonical tmux launcher supplies the required lifetime
boundary for the resumed queue in this environment.

At the final recovery handoff, the new scheduler PID was 78533, the monitor
PID was 78536, and the first successful new monitor sample was
`2026-09-13T04:06:21Z`. PORT Fish and SSS-GS bunny training had both emitted
real progress (steps 5,300 and 2,000 respectively). The queue snapshot was
12 completed, 2 running, and 29 pending, with GPU utilization 87% and 73%.
These are handoff observations; later phase scheduling belongs to the live
status file and monitor record.

## Cause boundary

The common stop of the scheduler, GS3 child, and PORT child, combined with
missing child tracebacks and a null scheduler failure record, supports a
common external termination or process-supervisor cleanup. The repository
does not contain the kernel signal, parent exit status, or supervisor log, so
it cannot distinguish a shell/tool cleanup, a cgroup or tmux-server cleanup,
or another host-level termination. The evidence does not support attributing
the event to a PORT model exception, a scheduler phase failure, or a cgroup
memory OOM.

## Recovery operation

After confirming that no old PIDs remain, launch the canonical script through
the host's persistent tmux server and use:

```bash
/workspace/ubuntu2004_cuda12_1/utils/conda-envs/ssd-gs/bin/python \
  /workspace/ubuntu2004_cuda12_1/projects/3dgs_relighting/PORT-GS/run_benchmark.py \
  --manifest /workspace/ubuntu2004_cuda12_1/projects/3dgs_relighting/PORT-GS/runs/full_benchmark_20260913/manifest.json \
  --resume
```

The queue and monitor logs remain under
`runs/full_benchmark_20260913/`. A future interruption should be diagnosed
from the scheduler PID, worker PIDs, last progress rows, queue log, and pane
exit status together; a `running` status alone is not evidence that a child is
still alive.
